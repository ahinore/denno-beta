### 1.3 なぜこれを選んだか

段の大きい順に潰すと、全部「測って棄却済み」か「`.cu` が要る」に落ちる (§8 の一覧)。
唯一 **大きい・ホスト側・値が変わらない・まだ太さを測っていない**のが、
14k の `pf_er` (早期 routing の先読み) の**並列度**だった:

- `er_MB=18,881` を**要求**しているのに、置き場へ入ったのは `ra_MB=11,284` (60%)。
  差は「窓の中で 8 本では読み切れない」ぶん。要求は既に「窓に収まる量」に
  絞られている (`DENNO_PF_EARLY_ROUTE_KB` = 24 KiB/token、task 486) ので、
  足りないのは帯域ではなく**同時発行**。
- 8 本を選んだのは task 474 (t470d: 14 本で 3.2-5.5 GB/s) と task 486
  (24 本で「窓を越えて MoE の写しと帯域を奪い合う」)。**どちらも MoE の写しが
  1 本の pread プールを共有していた頃の測定**で、task 558 (上げスレッドごとの
  プール) / 570 (3 本 + lookahead) / 546 (O_DIRECT バウンス) の後では事情が違う。
  これが「棄却済みを測り直す理由」。

## 8. 棄却済みとの関係 (なぜここだけが残っていたか)

3,826 の 87% / 14k の 67% はステージングのディスク待ちで、
読みの**形**は P530 (384 KiB) / P546 (O_DIRECT バウンス) / P550 (併合・4 MiB・
グループ) / P554 (上げ 2 本) / P558 (スレッドごとのプール) / P566 / P570 (3 本 +
lookahead) が 3 方向測って閉じている。14k の ssm は P577/P581/P592 が
「scan の直列和 = `.cu`」と特定。`other` の `iter_ple` は P357/419/423 が
本数 32/64/96/128/192/256 を測って 128 で閉じ、表の RAM 常駐は P182/P415
(28.8 GB) が捨てた。**残っていたのは先読みの並行度だけ**で、それは
「写しが 1 本のプールを共有していた頃」の 8 本のままだった (§1.3)。
