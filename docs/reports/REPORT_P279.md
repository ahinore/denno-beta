# task 279 — プールが借りる量を増やし、14k の prefill を 1 パスにする

task 279 (dev2)。branch `br279` は開始時の `int-auto` (`2a7dbf71e`) から。
`br270` (CHAIN_BIG / WORK_MB の配線、どちらも既定 off) を merge 済み。
測定はすべて GPU ラボ (SCENARIO=depth8k、PROFILE=1、MODEL=swift15-abl-IQ3_S)、3 ラウンド。

## 1. 結論 (3 行)

- **14k cold prefill は 16.76 / 16.80 s → 8.43 / 10.23 s (-39 / -50%)。** 目標
  (17.7 s から -15% = 15.0 s) を大きく上回る。3,826 cold は 3.33 / 3.65 →
  3.35 / 3.62 s で差なし、短い decode は 19.4 ms/tok で同一、14k 後の decode は
  20.8 / 20.4 → 19.5 / 20.4 ms/tok で悪化なし。errors 0、text sane。
- **勝ち筋はチャンクではなくタイル (MoE の 1 パスあたりのトークン数) だった。**
  14k の expert 重み H2D は 90.9 GB → 28.2 GB (-69%)、これは
  `DENNO_PF_LM_TILE` (既定 5,120 = 3 パス) を全トークン (1 パス) にしたぶんで、
  チャンクだけを 3,072 にした COND (t279a の c3k) は base と同値だった
  (パス数はタイルで決まり、チャンクは変えない)。
- 1 パスにすると作業域が 2,498 → 4,094 MiB に増え、その確保が expert を
  783 本 (1,622 MiB) 追い出す。借りた作業域を返すときに**その expert も LRU へ
  戻す**ことで、14k 後のヒット率は 0.956 (base) 対 0.959 (on) と悪化しない。

## 2. 前提

- 測定した木 = `3796e6b25` (= `2a7dbf71e` + br279 の 3 コミット + br270)。
  ラボの 3 ラウンドとも同じ木。**測定後に `int-auto` が動いた** (`9c5184c20`:
  task 269/275 の採用 = `DENNO_EXP_IQ_V3` と `DENNO_DEC_MIX_NORM_PAR` が既定 on) ので
  merge 済み (`f7d0f3727`)。下の数値はその前の既定に対するもの。
- 基準 COND はタスク指定の 4 本
  (`DENNO_EXPERT_IQ_GPU=1 DENNO_EXPERT_VRAM_MB=22000 DENNO_EXPERT_GPU_MIN_HIT=0
  DENNO_GPU_WEIGHT_MB=12000`)。各ラウンドの先頭に捨て COND (`x0`)、末尾に base の
  繰り返し (`base2`) を置いた。
- 1 パスの計画は 14k で 4,094 MiB を借りる (base は 2,498 MiB)。ラボの
  `[pf-pool]` は「空き 2011 → 217 MiB / 追い出し 783 本」「返した (空き 4847 MiB)」
  「大きい形で追い出した expert を 783 本 (1622 MiB) 戻した (0 本は戻せず)」。

### チャンクはパス数を変えない (t279a の c3k)

`DENNO_PF_CHUNK=3072 + DENNO_PF_CHAIN_BIG=1` (タイルは既定 5,120 のまま) は
14k cold 16.35 s (base と同値)、上げた重みも同じ 4 パス。**タスクの前提
「chunks × layers × miss rate」は、層優先の現行経路では「タイル数 × 層 × ミス率」
が正しい** (チャンクは mix / attn / ssm の反復数だけを変える)。

## 4. 変えたこと (3 コミット、既定 on は最後の 1 本)

1. `e788657e5` **`DENNO_PF_POOL_BIG`** — プールが借りられる量から
   (タイル, チャンク) を選ぶ。`pf_pool::choose_big` (純関数) が
   「パス数が少ない順 → チャンクが大きい順」に候補を試し、
   `DENNO_PF_POOL_BIG_MB` (既定 4,864 MiB) に収まる最初の組を採る。
   14k / TC で (タイル 14,018, チャンク 2,047) = 4,094 MiB = 1 パス。
   3,826 はタイルが既に全トークンなのでチャンクだけ 1,913 (2 枚) になる。
   ゲート off / 収まる組なし / 確保失敗のときは従来のチャンクとタイルへ戻す
   (リクエストは失敗させない)。**大きい形はプールを実際に借りられたときだけ**
   使う (t270a は作業域が取れず streaming が黙って落ちた)。
2. `e26c399c8` **追い出した expert も返す** — `DevBuffer::alloc_tagged` の追い出し
   経路が追い出した鍵を控え (`emergency_free_chunks_keys`、挙動は変えない)、
   プールの確保は自分の確保ぶんだけを `PF_POOL_EVICTED` に移す。大きい形を選んだ
   prefill は、作業域を返した後にその鍵を `pf_restore_experts` で LRU へ戻す
   (MoE 完了後 = 末尾の D2H の後なので t265b の衝突は起きない。本数は借りた量に
   比例して有界、実測 1,622 MiB)。
3. `3796e6b25` **チャンク既定 2,047**、本コミット **既定 on** — 2,048 以上は GDN
   連鎖の境界を越えるので `DENNO_PF_CHAIN_BIG` が要る。lab t279a ではチャンク
   2,047 (8.31 s) と 3,072 (8.46 s) で差が無かったので、未確認の形を既定にしない。

## 6. 採否

- 規則: 14k cold が 17.7 s から -15% (≤15.0 s)、3,826 cold が悪化しない、
  decode (短い / 14k 後) が +2% 以内、errors 0、text sane。
- 結果: 14k 8.43〜10.23 s (-39〜-50%)、3,826 差なし、短い decode 同一、
  14k 後 decode 悪化なし (19.5 / 20.4 対 base 20.8 / 20.4)、errors 0、text sane。
- よって **ADOPT: yes (t279c)**。`DENNO_PF_POOL_BIG` を既定 on にした
  (`0` / `off` / `false` / `no` で従来経路)。`DENNO_PF_CHAIN_BIG` は既定 off の
  まま (チャンク 2,047 では不要。2,048 以上を明示するときだけ要る)。

## 7. 数値の扱い

- 数値経路: 1 パスの版はチャンク (1,536 → 2,047) とタイル (5,120 → 全トークン) が
  変わるので、**丸め順と expert の選択履歴が変わる** (md5 DIFF はそのため)。
  演算も expert 選択も同じで、差は縮約のまとめ方だけ。
- 既定 off の経路 (`DENNO_PF_POOL_BIG=0`) は 1 バイトも変わらない
  (t279c の base / base2 / x0 は md5 SAME、t279a の c3k も SAME)。
- ホスト側の雑音が大きいラウンドがあった (同じ env で 8.43 vs 10.23 s)。
  数値はすべてラボの実測で、見積りは「推定」と書いた。

## 9. GPU で確認してほしいこと / 残した課題

1. merge 後の既定 (`DENNO_PF_POOL_BIG` 既定 on、int-auto `9c5184c20` の
   `DENNO_EXP_IQ_V3` / `DENNO_DEC_MIX_NORM_PAR` も on) で 14k cold が
   8.4〜10.2 s の帯に居ること。base が動いたぶん絶対値は変わりうる。
2. prefill 中にプール外の確保 (attention のミラー、gemv scratch) が空き不足で
   255 MiB のチャンクを追い出すことがある (t265 から未解決)。1 パス版は
   ピークの空きが 35〜217 MiB で、2 パス版 (3,043 MiB) は層 34 で 3 MiB の確保に
   失敗した。**作業域をプールへ移せば余裕ができる** (次の候補)。
3. `DENNO_PF_CHAIN_BIG` (br270) は既定 off のまま。チャンク 3,072 以上を
   明示するときのためだけに残してある (t279a で 3,072 は 2,047 と同速)。
4. `DENNO_PREFILL_WORK_MB` (br270 の配線) も既定 0。プールと併用すると
   予約と借りが二重に expert を追い出すので、両方立てないこと。
