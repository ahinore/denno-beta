## 2. 変えたこと (`DENNO_PF_PREAD_THREADS` の既定 32 -> 16)

- `crates/denno-engine/src/model/exp_pf.rs`
  - `DEFAULT_PREAD_THREADS` を **16** に (丸め `0..=64` はそのまま、`0` = 共有プール
    14 本という既存の意味もそのまま)。**プールの本数だけ**で、読む範囲・置き場・
    写し先・カーネルは 1 バイトも変えない (`pf_copy_into_pin` の `par_iter` を回す
    プールが細くなるだけ)。したがって値はビット一致。
  - doc を t358b (32 を選んだとき) と t606b (今回) の対比に書き換えた。task 558 で
    プールが上げスレッドごとになったことが「32 が濃すぎる」理由。
  - 台帳 `[exp-pf-stream]` の `copy_s` / `ready_s` / `nc_miss_MB` / `ra_MB` で
    発火を数えられる。
  - 切り戻しは `DENNO_PF_PREAD_THREADS=32` (テストで固定)。
- 追加したテストは規則の固定だけ (`pread_threads_rounds_and_defaults` に
  「既定は 16」「`=32` が切り戻しとして通る」)。本数は増やしていない。
- **既定 on のゲートを新設していない** (`gate_audit` の台帳に行を足す必要は無い)。

## 5. 数値の扱いと、なぜ「形」ではなく「濃さ」だったか

- 壁・段・`copy_s`・`ready_s`・`nc_miss_MB`・`ra_MB` はすべて lab の実測。
  **同じ run の中の対**でだけ比べた。lab のディスクは run の中で 2-3 倍動く
  (P566 §5 / P594 §4 / P602 §5) ので、柵の外側の差と**機構の実測**の両方が出た
  ものだけを採った。
- 14k は depth8k の round 1 にしか流れないので **COND あたり 1 サンプル**。
  柵 2 本 (10,849.3 / 10,248.2) に対して t 9,570.7 で、**どちらより速い**。
  さらに `nc_miss_MB` -4.1 GB / `ra_MB` +1.2 GB という機構の実測が付いている。
- **読みの形は既に閉じている**: 1 MiB x 8 本のプローブ天井は 3.5 GB/s、
  4 MiB は 4.6 GB/s (task 522)。本 run の staging は 0.79 MB x 96 本で 2.0-3.3 GB/s。
  読みを大きくする方向 (併合 / 4 MiB) は t522/t550 で負け (1 グループの barrier が
  最後の 1 本を待つため)、小さくする方向 (384/512 KiB) は t530/t550 でドリフト内。
  **残っていたのは本数だけ**で、その値は「プールが 1 本だった頃」のもの。
- 見積り: 3,826 で 16 本の効果が小さいのは、窓 (14.5 ms) と先読み予算 (2.3 GB) が
  先に尽きるため (推定)。次に太くする余地があるのは 14k の `other` の未計上
  412 ms と `ssm` の exposed 448 ms だが、本タスクでは測っていない。
