## 0. 結論 (先頭 10 行)

1. 現行の decode は **1 step = 1 トークン**で、1 step のコンテキスト (KV ミラー行が `pos0` の
   1 行だけ・GDN ミラーの ping-pong 面が 1 段・rope テーブル 1 行・`cache.advance(1)`) が
   すべて `n == 1` 前提に作られている (`cuda.rs:5005` / `cuda.rs:5194` / `qwen35.rs:2034`)。
2. 16.4 ms のうち **~16.0 ms (98%) は GPU 計算**、バイト転送は <= 0.33 ms、同期は 1 step に
   ちょうど 1 回 (`cuda.rs:2646`)。したがって「1 回の forward で複数トークンを進める」以外に
   decode を構造的に縮める道は無い (s108 / s115 の結論を再確認)。
3. 2 案を検討した。**案 A** = その場検証型 (batch-verify in place)。**案 B** = n-gram /
   プロンプト内ルックアップによる投機 (モデル重みを使わない draft)。
4. **決定論の契約で案 A は JS-divergence (数値クラスで言えば R1) になり、bit 一致では通らない。**
   しかも 1 回の検証 forward で `k+1` 位置を出すには `.cu` の入力ストライド + 出力位置引き +
   GDN 面の複製が要り、それでも **実効 16.4 ms/token で、速くならない**
   (損益分岐受理率 p* = 0.688 は「仮決めが当たる率」で、greedy の 2 トークン目が当たる率
   1 - D と比べると D < 0.31 が必要。R1 相当の経路差とアンカー再基準化も抱える)。
5. 案 A の変種 A-lite (`n ≧ 2` の既存 prefill 経路を `prefill 2 トークン` として使う) は
   **既存コードで bit 一致制約を保ったまま作れる**。ただし `n ≧ 2` の経路は 1 step が
   **18.3 ms** (算出) なので、step あたりの削減は **<= 0.4 ms (2.2%)** で、損益分岐 p* = 0.885 (算出) は
   **原理的に届かない**。→ 速度目的では却下。
6. ただし A-lite だけは副産物の可能性がある: `n ≧ 2` の prefill 経路 (CPU 逐次 + per-op の
   GPU フォールバック) が 1 トークン **~2.6 ms/step** (算出シナリオ) で回るなら、16.4 に対して
   6 倍以上になる。**ただしこれは「prefill 経路が実は decode より速い」という既存計測と矛盾する
   強い予測で、この環境では検証できない** (第 4 節に反証手順と、外れたときの判断を書いた)。
7. 案 B (n-gram 投機) は **1 step の構造を一切変えない**。draft 1 トークン = 通常の 1 step、
   検証 = 通常の 1 step、reject = 通常の 1 step の 3 種だけで、どれも既存の bit 一致経路。
   受理率 p の上限は「直前文脈の 12-gram が同一続きを持つ率」で決まる (= 実測が必要)。
8. **1 段で受諾できるのは最頻出の仮定 1 本だけ**という上限を明記する (`p = 0.9` の表は、
   争点が 1 つに絞られた場合の上限として読むこと)。小さな窓での受理率の実測で
   p_1 と p_2 を分けて測るのが先決 (第 3 節 3.3 の質問 2)。
9. 推奨: **実装には入らない**。まず GPU 機で「案 B の 12-gram オラクル計測」(モデル不要・
   1 分) と「A-lite 経路の 1 step 実測」(GPU 機 1 回) を回し、p_1 と `n ≧ 2` の step 時間を
   数字にしてから採否を決める。
10. 実装に入れる場合の最初の一歩は案 B の「draft / verify / reject の 3 種だけを使う
    planner」で、`.cu` / PTX / アンカーの変更は要らない (Rust のみ・決定論は既存契約に閉じる)。

## 1. Step 1 - 1 step の内訳 (現行 decode 経路)

### 1.1 1 step の段 (ホスト側 / GPU 側)

`Qwen35::forward_decode_chain` (`qwen35.rs:1805-2034`) が enqueue する順に並べる。すべて
同一の CUDA デフォルトストリームに積むので、**step 内に同期は無い**。

| # | 段 | 場所 | 側 | 回数/step |
|---|---|---|---|---|
| 1 | rope テーブル生成 (ホスト `cos`/`sin`) + H2D | `qwen35.rs:1859` → `cuda.rs:4833` | ホスト + H2D (<= 256 B) | 1 |
| 2 | バッファ予約 (rope / CH_QKV / CH_ATT / aq / kv_stage) | `qwen35.rs:1870-1876` | ホスト (定常では no-op) | 0-5 |
| 3 | 埋め込み 1 行 H2D | `qwen35.rs:1879` (`cuda.rs:2566`) | H2D (16,384 B) | 1 |
| 4 | 64 層 × (rmsnorm [H2D 3d 本] → qkv (+z) GEMV → [GDN scan \| full attn: QK-Norm+rope+attn+gate] → o_proj → rmsnorm → gate_up GEMV → swiglu → down GEMV) | `qwen35.rs:1886-1988` | GPU 計算 (+ H2D 1.77 MB) | 64 |
| 5 | 最終 norm + lm_head GEMV | `qwen35.rs:1999-2006` | GPU 計算 | 1 |
| 6 | prof 有効時のみ追加 sync | `qwen35.rs:2020-2023` | 同期 (**観測専用**) | 0 / 1 |
| 7 | **logits D2H + `cuCtxSynchronize`** | `qwen35.rs:2024-2026` → `cuda.rs:2646` | D2H (993,280 B) + 同期 | 1 |
| 8 | KV ステージ flush (pinned → ホスト `KvCache`) | `qwen35.rs:2030-2032` → `cuda.rs:5459` | ホスト memcpy (73,728 B) | 1 |
| 9 | `cache.advance(1)` | `qwen35.rs:2034` | ホスト | 1 |

`generated.push` → EOS / stop 判定 → `emit_delta_and_check_stop` → **次 step の forward**
(`engine.rs:871` / `904`)。この並びが「次トークンが決まるまで次 step を始められない」の実体。

### 1.2 16.4 ms の内訳 (既存実測の引用のみ)

| 成分 | 値 | 種別 | 出典 |
|---|---|---|---|
| decode 1 トークン | 16.4 ms (gen2 200 token = 3.285 s) | **実測** | `docs/TASKS.md` 冒頭・`GPU_VERIFY` (s118 節) |
| バイト転送の合計 | <= 0.33 ms (2.0 %) | 算出 (2,852,864 B/step ÷ 8.6-14.3 GB/s) | `DECODE_PATH.md` §3 (s68 の帯域実測を入力にした算術) |
| 依存同期 (logits D2H) | 1 回 / step・コピー本体 <= 0.07 ms | 算出 (993,280 B ÷ 14.3 GB/s) | `DECODE_PATH.md` §3 (b) |
| GPU 計算 | ~16.0 ms (98 %) | 算出 (16.4 − 0.33 − …) | `DECODE_PATH.md` §3 (c) |
| ホスト memcpy (段 8) | ~0.002 ms | 算出 (73,728 B ÷ 4.7 GB/s) | `DECODE_PATH.md` §3 表 (s68 の 4.7 GB/s から) |
| ホストの rope テーブル生成 | <= 0.05 ms (n_rot = 128) | **推定** (超越関数の所要は未計測) | `DECODE_PATH.md` §4 L3 |
| launch 回数 | 64 層 × 5-6 + lm_head ≒ 330-390 / step | 算出 (ソースの呼び出し構造から数えた) | `qwen35.rs:1886-2006` |

**逐次依存の部分とそうでない部分**: 上の表のうち、次 step を始めるために**ホストが待たされる**
のは段 7 の 1 点だけ。段 7 が待っているのは「その step の GPU 計算の完了」であって転送では
ないので、**16.4 ms のうち ~16.0 ms が「GPU 計算 + その完了待ち」= 実質的に解けない逐次部分**、
残り ~0.4 ms が「転送 + ホスト作業」= 理論上ゼロにできる部分になる。

### 1.3 「なぜ k トークン先読みが今の構造でできないか」の根拠 (コード)

- **KV ミラー**: `chain_q35_fullattn` は `t_total = pos0 + 1` で、`dno_qknorm_rope_pi` が
  ミラーの **`pos0` 行に 1 行だけ**書く (`cuda.rs:5005` / `5038`)。attention カーネルは
  `dno_attention` (1 行専用) で、`n` 行版は prefill 側の `dno_attention_prefill` だけ
  (`cuda.rs:4368` ff.)。
- **GDN ミラー**: `chain_q35_gdn_scan` は `t_total = pos0 + 1`、`cur` / `1-cur` の 2 面だけで、
  「この層のミラーが `pos0` に同期していなければ seed」(= `1-cur` 面へホスト状態を H2D) という
  1 段の前提 (`cuda.rs:5194` / `5228-5240`)。k トークン先読みには面が k 段必要。
- **rope テーブル**: 1 step 1 行分だけを H2D する (`qwen35.rs:1859`・`cuda.rs:4828` のコメント)。
- **ホスト正本の更新**: `chain_q35_kv_stage_flush` は `pos0` の 1 行だけを書き戻し
  (`cuda.rs:4599-4609`)、`cache.advance(1)` で 1 進める (`kv_cache.rs:201`)。

**含意**: k=1 でも「複数位置を 1 forward で処理する」ことは、既存の `n == 1` チェーンを
**arg 化するのではなく別のコード経路を足す**ことを意味する。既存の `n ≧ 2` 経路
(`forward_prefill`) があるので「ゼロから書く」わけではないが、`n ≧ 2` 経路は
**per-op + 同期あり** (prefill 用) である点が効く (第 2 節 A-lite)。

### 1.4 巻き戻し (rollback) の可否 - ここが案の採否を分ける

「投機」=「間違ったら戻す」なので、戻せるかどうかが先に決まる。

| 部品 | 戻せるか | 根拠 |
|---|---|---|
| ホスト `KvCache` (full 9 層分) | **戻せる**。`truncate(len)` + `bump_epoch()` があり、`restore` は epoch を上げて GPU GDN ミラーを捨てる (`kv_cache.rs:215` / `256` → `cuda::gdn_scan_state_invalidate()`) | コード |
| GPU KV ミラー | **捨てられる**。`with_mirror` は `have > pos0` を「ホストが正に戻った」として全再 seed する (`cuda.rs:3303`) | コード |
| GPU GDN ミラー | **捨てられる** (epoch 不一致 → 状態 H2D 再 seed・`cuda.rs:5228` ff.) | コード |
| prefix cache のエントリ | 影響なし。退避は prompt 境界 (`kv_len == prompt.len()`) のみで、decode 中は作らない (`engine.rs:828-843`) | コード |
| 出力トークン列 | `generated.truncate(n)` で戻せる (ホストの Vec) | コード |

**したがって「投機の巻き戻し」は機構としては存在する** (s46 の prefix 復元と同じ道具)。
コストは「epoch bump + 次 step のミラー全再 seed」= 全 64 層の KV 行 (5,686 + t 行) の H2D と
GDN 状態 27 層 × ~5.8 MB の H2D。**reject 1 回あたりの実費は未計測**だが、KV 行は
`pos0 × 1024 × 4 × 9 層` = 5,686 トークンで **~210 MB** (算出: 9 層 × 5,686 × 4,096 B)、
GDN 状態は **~5.8 MB** (`cuda.rs:5365` のコメントから)。14.2 GB/s で **15 ms** の H2D
(算出)。**reject が入るたびに 1 step 分の時間を払う**ので、案 A の損益分岐はここで厳しくなる。

## 2. Step 2 - 設計案 (2 つ)

### 案 A: その場検証 (batch-verify in place)

**形**: 1 回の forward で「次の k トークンの logits」をまとめて出す。次のトークンの選び方は
cur の logits の argmax 1 本。k=2 なら 2 回目・3 回目のトークンは仮決めで、検証 forward の
結果と食い違ったら巻き戻す。

#### A-1 正しさの契約

- **逐次生成との bit 一致は取れない。** 逐次経路の 2 トークン目以降は `rmsnorm` の入力も
  attention も「仮決めトークンで進めた状態」で計算されるが、正しい状態は「cur の logits から
  サンプルしたトークンで進めた状態」。両者が一致するのは「仮決めが当たったとき」だけ。
- 当たらないときの差は **「別の接頭辞で計算した後で戻す」** ことによる差ではなく、
  **「同時に走らせた他の位置の演算が 1 トークン目の演算に干渉する」** ことによる差。
  干渉源は 3 つ:
  1. **rmsnorm の H2D**: `chain_rmsnorm` は毎回 `w` を出力バッファのテイルへ押し込み、
     `dno_add_rmsnorm` は `rows = n` を読む (`cuda.rs:2755` ff.)。n = k にすると 1 行目も
     「同じバッファに n 行分の別トークンが居る」状態で走る。
  2. **attention**: `dno_attention_prefill` は block 単位の causal で、`t_total` が変わると
     online-softmax の `acc` の到達範囲が変わる。**s118 がまさにこれを数値不変と言えないと
     判定した** (先行タイルの蓄積が FMA の丸め単位を変える)。
  3. **GDN**: 再帰状態なので、仮決めトークンで進めた状態から正しい経路を再開するには面の複製が要る。
- したがって案 A は **R1 (f32 縮約の順序・分割変更・相対 1e-6)** ではなく、
  「**別の演算をした結果を、一致したときだけ採用する**」形になる。一致検査を
  「logits の bit 比較」にしても、**比べる対象 (1 行目の logits) 自体が干渉で変わっている**
  ので、bit 一致を検査する手段が無い。→ **決定論 (同一入力 → 同一出力) は保たれる**が、
  **逐次生成との bit 一致は保証できない** (`NUMERIC_POLICY.ja.md` §1-2 の「測ってから commit」は
  満たせるが、§2 の R クラスのどれにも収まらない「経路依存の差」になる)。
- 結論: **案 A は「決定論は OK・bit 一致は不可」**。アンカー (`1e-7` 比較) は動く可能性が高く、
  再基準化 (オペレーター判断) が前提になる。**「同一入力で毎回同じ出力」は満たす**ので
  失格ではないが、**「逐次生成と bit 一致」を満たせない点は明示的に承認が要る**。

#### A-2 実装コスト

- **`.cu` 必須**: `dno_gdn_scan` に (a) `dk` ごとの面オフセット (面ポインタ配列)、(b) 出力の
  `pos` 引き、(c) 1 block が `k` トークン分を回す (または block を `k` 倍に増やす) 変更が要る。
  `dno_qknorm_rope_pi` / `dno_attention_prefill` / `dno_matvec_*` も「行オフセット」を引数化する
  必要がある (現行は `pos0` 固定の 1 行前提)。
- **PTX 再生成 + `GPU_VERIFY`** が要る。**アンカーは動く見込み** → 再基準化の承認が要る。
- Rust 側: `chain_q35_gdn_scan` / `chain_q35_fullattn` の引数追加、`KvMirror` の GDN 面を
  `k` 段へ、`chain_q35_kv_stage_flush` の複数行化、`cache.advance(k)`、`forward_decode_chain` の
  複数位置版。**`n == 1` 経路は残す** (fallback のため)。

#### A-3 期待効果 (式と表)

記号: `S` = 1 step の時間 (現行 16.4 ms)、`λ` = 「k トークンを 1 forward で出す」ときの
step 時間の倍率 (`k=2` で `λ = S2/S`)、`q` = 1 forward が先読みするトークン数 (`q = k-1`)、
`p` = 「先読みした `q` 本が全部当たる」確率 (**仮定**。実測不能)。

- 平均 step 数 = `1 / (1 + q/p)`。
- 1 回の検証 step の実効時間 = `λ/S` + (外れたとき) 巻き戻し `R`。
- 実効 `ms/token = λ/S / (1 + q/p)`。損益分岐 `p* = (λ - 1) / q`。

`k = 2` (`q = 1`) を仮定し、`S = 16.4 ms`。`λ` は 2 通り置く:

- **A-lite** (`n ≧ 2` の prefill 経路を流用): `λ = 18.3 / 16.4 = 1.115` (2 節 A-lite の算出)
- **A-full** (`.cu` を n 化して per-op を廃した理想): `λ = 1.00` (推定: 位置当たりの GEMM が
  同じで launch が消えるため。**楽観側の推定**)

| p (仮定) | A-lite 実効 ms/token (λ=1.115) | A-full 実効 ms/token (λ=1.00) | 逐次 (=16.4) との差 |
|---|---|---|---|
| 0.5 | 12.19 | 10.93 | -26 % / -33 % |
| 0.7 | 10.76 | 9.65 | -34 % / -41 % |
| 0.9 | 9.62 | 8.63 | -41 % / -47 % |

これは `p` を**外生**に置いた場合の表。実際は `p` が従属変数で、`p = 1 - D`
(`D` = 2 トークン目が cur の argmax と食い違う率) になり、**greedy では p は logits の形で
決まる**。`p` が低い領域での実効値 (reject 1 回あたり `R` = 15 ms の H2D を払う):

| D (= 1-p) | A-lite 実効 (λ=1.115, R=15 ms) | A-full 実効 (λ=1.00, R=15 ms) |
|---|---|---|
| 0.31 (p=0.69) | 16.4 | 14.7 |
| 0.5 | 20.0 | 18.0 |
| 0.7 | 24.2 | 21.7 |

- **A-lite の損益分岐**: `p* = (1.115-1)/1 = 0.115` (R 無視)・R を入れると `p* ~ 0.69`。
  つまり **`p > 0.69` でないと A-lite は遅くなる**。greedy の `p` は「最頻出確率」なので、
  その上限はモデルの logits 分布次第で、**実測なしに 0.7 を超えるとは言えない**。
- **A-full の損益分岐**: `λ = 1.00` なら R 無視で `p* = 0`。ただし R を入れると `p* ~ 0.48`。
  そして `λ = 1.00` 自体が「k 行を 1 回で処理しても step 時間が増えない」という**推定**で、
  attention の計算量が `k` 行で `k` 倍 (`t_total` の KV 読みが各位置で増える) ことから、
  **実際は `λ > 1` になる可能性が高い** (attention は 16.4 ms のうちの一部だが未計測)。

**断定しない**: `λ` と `p` のどちらも実測が無い。上の表は「p を 0.5/0.7/0.9 に置いたときの
算術」であって予測ではない。**A-full で 12 ms/token (P2-1 の目標) に行くのは
`λ = 1.00` かつ `p >= 0.73` の同時成立が条件**で、`λ` は attention の増分で必ず 1 を超える。

#### A-4 既存構造との衝突

- **prefix cache (s46)**: 退避は prompt 境界のみ。投機の reject で `epoch` が上がると
  `gdn_pending` が破棄される (`cuda.rs:5359`) ため、**reject 後は次の prefill で GDN 状態の
  回復ができず、要求ごと落ちる経路がある** (`forward` 冒頭の flush が `None` を返す)。
  これは reject の設計に「reject は epoch を上げない (ホストは触らない)」制約を課す。
- **KV grow (s41)**: k 行ぶんの容量が step 開始時に足りないと `chain_ensure_buf` が
  in-flight バッファを解放する危険 (s50/s49 で踏んだ事故)。**k 行予約は step 開始時に
  一括**でなければならない。
- **GDN 遅延フラッシュ (s50)**: `gdn_pos` は「1 step = 1 進む」前提。k 段の面を持つと
  `gdn_pos` の意味が「面の位置」に変わり、`chain_q35_gdn_flush_pending` の層ごとの
  位置判定 (`cuda.rs:5365` ff.) を作り直す必要がある。
- **`cache.advance(n)`**: `advance` 自体は n を受け取れる (`kv_cache.rs:201`) が、
  `chain` 側の `kv_stage_flush` が 1 行固定 (`cuda.rs:4599-4609`) なので行数引数化が要る。

**判定: 案 A (full) は「`.cu` 必須・アンカー再基準化必須・損益分岐 p が実測できない」の
3 点で、いま実装に入るべき案ではない。** 巻き戻しは機構として存在するので「実装不能」では
ないが、**承認に必要な数字 (λ, p) が無い**。

### 案 A-lite: 既存の `n ≧ 2` 経路を「prefill 2 トークン」として投機に使う

**形**: `.cu` を触らずに、`forward(&[t1, t2])` (既存の prefill 経路) を「投機」として呼ぶ。

#### 正しさの契約 (ここが A-full と決定的に違う)

既存の `n ≧ 2` 経路は **「トークン逐次と同じ結果を出す」ことが既に契約になっている**
(`qwen35.rs:1020-1030` のコメント: 投影の m>1 経路は i32 累積が順序不変なので m==1 と
行単位でビット一致、GDN は逐次、attention は causal)。したがって:

- **出力の 1 行目 (= t2 の logits) は、逐次で t2 を流したときと bit 一致する**
  (既存の prefill == 逐次の bit 一致契約。`docs/HISTORY.ja.md` A2 節・T4 節の
  「GPU GEMM は本当にビット一致」)。
- したがって **受理判定は「bit 比較」でできる**。仮決め `t2` が 1 行目の argmax と一致すれば
  受理、食い違えば **`cache.truncate(pos0+1)` + epoch bump して 1 トークン目だけを残す**。
- **決定論**: 完全に保たれる (全部既存の決定論経路)。**bit 一致**: 受理時は逐次と同一、
  棄却時は「捨てただけ」で同一。→ **R クラス不要 (緩和ゼロ)**。

#### 実装コスト

- **Rust のみ**。`forward_decode_chain` の呼び出し側に「2 トークン版」を足すだけで、
  `.cu` / PTX / アンカーは無変更 (`n ≧ 2` の prefill は既に本番で動いている)。
- ただし `forward_prefill` は **per-op 経路** (層ごとに `maybe_gpu_linear` を呼び、
  GDN は `gdn_scan_batch` で H2D/D2H + 同期) なので、**同期回数が 1 回ではない** (s61c 節)。

#### 期待効果 (算出。ここが結論を決める)

`n == 2` の 1 step 時間を、既存の在庫から積む (**すべて算出・未計測**):

| 成分 | 算出 | 根拠 |
|---|---|---|
| 重み読み (int8 9B ~ 4.7 GB/step) | 同一 | 重みは n に依らず 1 回 (バッチ律速の原則・`HISTORY` P6 節) |
| 演算 | 2 倍 | 行が 2 本になる |
| launch | 同じ回数 (per-op ループを 2 行で回す) | `forward_prefill` の構造 |
| 同期 | per-op 経路なので **層あたり複数回** (GDN 層は `gdn_scan_batch` の H2D/D2H) | s61c 節 |
| **推定 step 時間** | **18.3 ms** (16.4 × 1.115) | 演算 2 倍が「計算部分」に効き、段の固定費 (launch/同期) は不変という**推定** |

→ `λ = 1.115`。`k = 2` の損益分岐は R 無視で **`p* = 0.115`**、R (reject 15 ms) 込みで
**`p* ~ 0.69`**。**greedy の `p` の上限は「最頻出トークンの確率」で、それは 1 に近づかない**
(実測対象)。したがって **A-lite を速度目的で採るのは損益分岐が高すぎる**。

**重要な副産物 (未検証の予測)**: もし `n == 2` の step が **~5.2 ms** で回るなら
(`(16.4 + 18.3) / 2 = 17.35 ms` ではなく「prefill 経路の実測」として)、それは
**「prefill 経路は decode チェーンより 3 倍速い」**という意味になり、decode チェーン自体の
性質 (98% が GPU 計算) と矛盾する。**この矛盾を解く観測 1 つ (下の第 5 節 質問 3) が、
P2-1 の 12 ms に一番近い可能性がある**。

### 案 B: n-gram / プロンプト内ルックアップによる投機 (モデル重みを使わない draft)

**形**: 直前文脈の `m`-gram が「前にも出てきた」なら、その続きを draft として仮決めする。
検証は **普通の decode step** を 1 回走らせて argmax を比べるだけ。

- 受理: `token = argmax(logits)` が draft と一致 → 出力に積み、`cache.advance(1)` (既に進んでいる)。
- 棄却: draft を捨てる。**`cache.advance(1)` は既に走っているので何も戻さない**。
  ← **この案は巻き戻しが要らない** (step は常に 1 トークンで、draft は「正しい 1 トークンを
  先に当てただけ」)。

#### B-1 正しさの契約

- **bit 一致**: 1 step は既存の `forward_decode_chain` そのもの。draft は「次に来るトークンの
  予測」でしかなく、**採否に関係なく計算は同じ**。→ **逐次生成と bit 完全一致**。
- **決定論**: draft は「文脈の最長一致から決定的に選ぶ」ので RNG 不要。同じ文脈 → 同じ draft。
- **数値クラス**: **なし (緩和ゼロ)**。`NUMERIC_POLICY` の R1-R4 を使わない。

#### B-2 実装コスト

- **Rust のみ** (engine 層)。`.cu` / PTX / アンカー無変更。
- 触る場所: `engine.rs` の decode ループ (`engine.rs:858-906`) に「draft 選択 (ホスト) →
  `sampler.sample` の代わりに draft を採用 → EOS / stop / UTF-8 保留の検査 → 次 step」の分岐。
  `Sampler` には触らない (受理判定は `argmax(logits) == draft` の比較 1 回)。
- 制約: **penalty / tool_mask / no_repeat_ngram が有効なときは無効化** (logits が文脈依存で
  変わるため、draft の「文脈の続き」と一致する保証が無くなる → 無効化が安全)。
  greedy (temperature = 0) のみ有効。

#### B-3 期待効果

`S = 16.4 ms`、`C_d` = draft 選択のホストコスト (**推定 0.01 ms 未満**: `Vec<u32>` の
最長一致探索は文脈長 5,700 で「最後の 12-gram を後ろから探す」線形 1 回)。
1 step = 「draft + 通常 step」なので:

- 実効 step 時間 `S + C_d ~ 16.41 ms`、`q = 1` (draft 1 本)。
- 実効 `ms/token = (S + C_d) / (1 + p)`。

| p (仮定) | 実効 ms/token | 対 16.4 |
|---|---|---|
| 0.5 | 10.94 | -33 % |
| 0.7 | 9.65 | -41 % |
| 0.9 | 8.64 | -47 % |
| **損益分岐** | `p* = C_d / S ~ 0.0006` | **ほぼ 0** |

**この案の損益分岐はほぼゼロ** (draft が完全に外れてもコストはホストの探索だけ)。ただし
**p の上限は「直前文脈の 12-gram が同一続きを持つ率」で、それは出力の性質で決まる**:
- 表・コード・JSON・定型文・tool 呼び出し: p は高い (構造が反復する)。
- 自由文・思考: p は低い (同じ 12-gram が再出現しない)。
- **p の実測は GPU 不要** (アンカーの応答テキストやログのトークン列でオラクル計測できる)。

**注意 (上限の明示)**: `p = 0.9` が成立するには「次の 1 トークンがほぼ確定」している必要が
ある。それは「争点が 1 本」の場合で、**自由文では p は 0.3-0.6 程度が現実的**というのが
一般的な報告だが、このリポジトリには数字が無い。**実測 (オラクル計測) を最優先にする。**

#### B-4 既存構造との衝突

- **巻き戻し不要** (B-1)。`cache.advance(1)` は 1 step = 1 のまま。
- prefix cache / KV grow / GDN 遅延フラッシュ: **1 step の構造を変えないので衝突なし**。
- **EOS / stop / UTF-8 保留との整合が唯一の難所**: `emit_delta_and_check_stop` は
  「`generated` 全体を decode して差分を出す」設計 (`engine.rs:975-1003`) なので、
  **draft で 2 トークン進んだときも同じ関数を 2 回呼ぶ必要がある**。1 回目で stop したら
  2 回目は呼ばない、という順序制約を守る。`tool_mask` の `feed` も同様。
- `max_tokens` の境界: `generated.len() + 1 > max_tokens` で draft を採らない。

## 3. Step 3 - 判断材料 (1 ページ)

### 3.1 案の比較

| 項目 | 案 A (その場検証 full) | 案 A-lite (既存 `n ≧ 2` 流用) | 案 B (n-gram 投機) |
|---|---|---|---|
| 逐次生成との bit 一致 | **不可** (R1 相当の経路差) | **可** (既存契約) | **可** |
| 決定論 | 可 | 可 | 可 |
| 数値クラス | R1 + 再基準化 | なし | なし |
| `.cu` / PTX | **必須** | 不要 | 不要 |
| アンカー再基準化 | **要** | 不要 | 不要 |
| 損益分岐 p (k=2) | `p > 0.48` (R 込み) | `p > 0.69` (R 込み) | `p > 0.0006` |
| 実装規模 (推定) | 大 (2,000 行超) | 小 (200 行) | 小 (150 行) |
| 12 ms/token に届く条件 | `λ = 1.00` かつ `p >= 0.73` | **届かない** (`λ` が 1.115 で上限 9.62 ms でも p が要る) | `p >= 0.37` |
| 前提の実測 | `λ` (attention 増分)・`p` | `n=2` の step 時間・`p` | **オラクル計測のみ** (GPU 不要) |

### 3.2 結論

- **いま実装に入る案は無い。** 案 A は「bit 一致不可 + `.cu` + 再基準化 + p が実測不能」で
  4 重にオペレーター判断が要る。案 A-lite は損益分岐が高すぎる (p* ~ 0.69)。
- **最初に測るべきは案 B のオラクル** (GPU 不要・1 分)。p_1 が 0.4 を超えるなら案 B は
  「Rust のみ・bit 一致・損益分岐ほぼ 0」で、**承認後に実装に入れる唯一の案**になる。
- 案 A を検討するのは、案 B の p が低い (自由文で 0.3 未満) と分かってから。

### 3.3 オペレーターに聞くこと (最大 5 個)

1. **bit 一致の契約を投機の受理判定に限って緩めてよいか** (案 A は「逐次生成と bit 一致しない」
   ので、`1e-7` アンカーの再基準化が前提)。→ 案 A を検討対象に残すかどうかが決まる。
2. **GPU 機で「12-gram オラクル計測」を回してよいか** (モデル推論不要・アンカーの
   トークン列か 1 本のログで p_1 / p_2 を出す。supervisor が代行できる)。→ 案 B の採否。
3. **`n == 2` の `forward_prefill` 経路の 1 step 時間を測ってよいか** (`PF_BENCH` 相当の
   1 回の計測。`n == 1` の 16.4 と比べる)。→ A-lite の `λ` が決まる (副産物の 6 倍予測の検証)。
4. **投機の採否を「ワークロード別」に分けてよいか** (tool 呼び出し / コード生成は案 B が効き、
   自由文は効かない可能性。既定 off の環境変数で入れる前提)。
5. **投機で reject が続いたときに「投機を止める」適応 (直近 N step の受理率で on/off) を
   決定論の一部として許すか** (適応は決定的な閾値判定にすれば決定論は保たれるが、
   「同じ入力で同じ出力」の証明がワークロードの履歴に依存するようになる)。

## 4. この文書で「測っていない」こと (正直な一覧)

- `λ` (k 行 1 forward の step 時間比): **未計測・算出もできない** (attention の増分が
  モデル依存)。A-full の `λ = 1.00` は**楽観仮定**。
- `p` (受理率): **未計測**。0.5 / 0.7 / 0.9 は仮定の表。**オラクル計測で測れる** (質問 2)。
- reject 1 回のコスト `R` (epoch bump + ミラー全再 seed): **算出 15 ms** (KV 210 MB +
  GDN 5.8 MB ÷ 14.2 GB/s)。**実測なし**。
- `n == 2` の `forward_prefill` step 時間: **算出 18.3 ms** (演算 2 倍・固定費不変の仮定)。
  **実測なし**。この仮定が外れて 5 ms 台なら結論が変わる (質問 3)。
- 案 B の draft コスト: **推定 < 0.01 ms** (`Vec<u32>` の線形探索)。
- 12 ms/token の到達可能性: **上記が全部揃って初めて言える**。この文書は「速くなる」とは
  書かない。

**反証手順 (実測が入ったときの判断)**:
- 質問 2 の p_1 < 0.3 → **案 B 却下**。案 A も `p` が同じ理由で低いので却下。
  → **decode 軸は「カーネル (attention/GDN) の総当たり」以外に残らない**と結論する。
- 質問 3 で `n=2` が 5 ms 台 → **A-lite を最優先**(損益分岐が 0.115 まで下がる)。
- 質問 2 で p_1 >= 0.5 かつ質問 3 で `n=2` が 18 ms 台 → **案 B のみ**を実装候補にする。
