# 第1巻 ブートストラップ — 単一バイナリから CI まで

> [索引](README.md) / 次: [第2巻 API 機能](10_api_features.md)

対象期間: 2026-10-11(初期実装)〜 P2 完了。担当範囲のうち最も古い区間で、まだ GPU も量子化も無い。
日付は commit の author date を JST で表す。

## この巻で分かること

- 単一バイナリ(cli / engine / server)構成と、Anthropic Messages API 互換を最初に選んだ理由
- exact decoding(seed 固定・貪欲・同一入力→同一出力)を最初から基準に据えたことの帰結
- KV キャッシュと prefix cache の 2 段階(P1 = 単一エントリ → P2 = マルチエントリ LRU)
- Docker 配備と CI の立ち上げ、ビルド対象 CPU を x86-64-v3 に固定した理由

## 前提知識

Rust / Cargo workspace、transformer の forward と KV キャッシュ、Anthropic Messages API と SSE、Docker のマルチステージビルド。
量子化・CUDA・GGUF はこの巻には出てこない(巻3 以降)。

### 初期実装: 単一バイナリと Anthropic 互換 API (2026-10-11, `7f85369`)

- **意図**: 学習用に「読める」LLM サーバーを 1 リポジトリで完結させたかった。既存の推論エンジンを持ち込まず forward とサンプラを自分で書く前提だったため、対象アーキテクチャを GPT-2 と Qwen2/Llama 系の 2 系統に絞った。API は当時使っていたクライアントが Anthropic Messages API を話すので互換側に合わせ、CLI とサーバーで同じ engine を使うために crate を 3 つ(cli / engine / server)へ割った。

- **変えたもの**
  - `7f85369` — 22 ファイル / +4,276 行。
  - `crates/denno-engine/src/{load,tensor,tokenizer,sampler}.rs`、`model/{gpt2,llama,mod}.rs`。
  - `crates/denno-server/src/lib.rs`、`docs/PLAN.md`、`docs/api.md`。

- **つまずき**
  - 症状: 実モデルを通すと出力が意味を成さない。ストリーミングもクライアントから正しく解釈されない。
  - 原因: 初回コミットは「形が通る」ところまでで、数値の正しさを判定する手段が無かった。API の形を先に固定したため、実モデルの疎通と SSE の仕様差が未解決のまま残った。
  - 抜け方: 数値側は次のコミット、SSE 側は 2 つ後のコミットで個別に潰した(この巻の続き)。

- **分かったこと / 残った課題**
  - engine を crate に切っておくと、同じ forward を CLI からもサーバーからも叩けて検証が回しやすい。
  - 一方で「正しさ」の基準が無く、出力が合っているかを毎回目視で見るしかなかった。

- **次に効いたこと**: 「同じ engine を CLI から直接叩ける」構造が、後の exactness テスト(実モデル無しで合成モデルを回す)と、CPU 参照とのビット比較の土台になった。

- **変えたもの**

- **変えたもの**

  - attention をスカラーループから sgemm へ(`model/llama.rs`)、`.cargo/config.toml` で `target-cpu=native`。
  - `crates/denno-server/src/lib.rs` の SSE event 名と ping keep-alive、`examples/bench_gemm.rs` の追加。

  - 原因: SSE の event 名が Anthropic 形式と一致しておらず、無通信時間を埋める ping も無かった。
  - 抜け方: event 名を仕様に合わせ、ping keep-alive を足した。commit 件名に「works with Hermes agent」とあり、ここで初めて実クライアントと繋がった。

- **分かったこと / 残った課題**

### P1: KV キャッシュと単一エントリの prefix cache (2026-10-11, `831246b`)

- **意図**: 同じ system プロンプトと履歴を毎ターン作り直すのが最大の無駄だった。KV をリクエスト間で保持し、次回の prefill をほぼ 0 にすることが目的。

- **変えたもの**
  - `831246b` — +76 / -12。
  - `engine.rs` にリクエストをまたぐ KV 再利用、`kv_cache.rs` の追加。
  - `tensor.rs` の decode matvec 出力分割並列化、`model/llama.rs` の対応。

- **つまずき**
  - 症状: 2 回目の同じ会話は速いが、別の会話が来た瞬間に元に戻る。
  - 原因: prefix cache が「単一エントリ」なので、新しいプロンプトで前のエントリを捨てていた。
  - 抜け方: この制約は P2 でマルチエントリ LRU にするまで残した。decode matvec の並列化は出力要素の分割で、累積順を変えないため数値は不変。

- **分かったこと / 残った課題**
  - 2 回目以降の prefill は 1,519 トークン → 11 トークン相当まで落ちた(HISTORY §2 の要約表。モデル・プロンプトの明記は無い)。
  - 残った課題は「単一エントリでは交互セッションで効かない」こと。

- **次に効いたこと**: 「KV を捨てずに済むなら捨てない」という方針が、後の KV 予算設計(需要ベース確保・スロットプール)と、recurrent モデルで状態をどう保存するか(巻3 の GDN スナップショット)まで一貫して続く。

### Docker 配備 — マルチステージビルドとモデル自動取得 (2026-10-11, `f1c3bde`)

- **意図**: 手元でビルドしたバイナリを持ち回る運用をやめ、`docker compose up` で立ち上がる形にしたかった。モデルの取得も起動時に寄せた。

- **変えたもの**
  - `f1c3bde` — +73 / -0。
  - `Dockerfile`(マルチステージビルド)、`docker-compose.yml`。
  - `docker/entrypoint.sh`(起動時のモデル自動取得)。

- **つまずき**
  - 症状: モデルを替えるたびにイメージを作り直すことになる。
  - 原因: ビルド成果物とモデルキャッシュを同じイメージ層に入れていた。
  - 抜け方: ビルド段と実行段を分け、モデルはボリューム側へ。entrypoint が取得済みかどうかを見て DL を省く。

- **分かったこと / 残った課題**

- **次に効いたこと**: 起動スクリプトに設定を閉じ込める発想は、後の本番起動スクリプト(量子化・KV 予算・temperature 上限をフラグで固定する形)にそのまま引き継がれた。

- **変えたもの**

### CI の SIGILL 修正 — ビルド対象を x86-64-v3 に固定 (2026-10-11, `37cc6b0`)

- **意図**: CI がランナーによって落ちるようになった。原因を潰して、push ごとに同じ判定が出る状態に戻す。

- **変えたもの**
  - `37cc6b0` — +11 / -0。
  - `.github/workflows/ci.yml` のみ。`target-cpu` を `native` から `x86-64-v3` に固定し、キャッシュキーを更新。

- **つまずき**
  - 症状: CI が SIGILL(不正命令)で落ちる。
  - 原因: `rust-cache` がランナーの CPU 世代をまたいでビルド成果物を共有するため、新しい CPU 向けにビルドしたバイナリが古いランナーで実行される。
  - 抜け方: ビルド対象を最小公約数の命令セットに固定する — `native` を捨てて `x86-64-v3` にした。

- **分かったこと / 残った課題**
  - キャッシュは速いが、CPU 機能を暗黙に固定してしまう。開発機で `native` を使うことと CI で再現性を取ることは両立しない。
  - 以後「CI は x86-64-v3 で全緑」が合否の前提になった。

- **次に効いたこと**: 「同じ入力なら同じ出力」を機械の側でも保証する必要があるという認識が、exactness ジョブの運用に繋がった。後にアンカー md5 を GPU と CPU で取り分ける判断も、この延長にある。

## 棄却カタログ

当時は妥当に見えたが後で捨てた判断。棄却の理由は、そのときに観測できた事実で書く。

### `target-cpu=native` を CI のビルド対象に据え続ける(`37cc6b0` で棄却)
- 採用理由: 開発機の命令セットをそのまま使えば速い。この巻の時点では最適解だった。
- 観測: CI が SIGILL(不正命令)で落ちる。`rust-cache` がランナーの CPU 世代をまたいでビルド成果物を共有するため、新しい CPU 向けのバイナリが古いランナーで実行される。
- 棄却: ビルド対象を最小公約数の `x86-64-v3` に固定。開発機の `native` と CI の再現性は両立しないと分かった。

### prefix cache を単一エントリのまま据え置く(`6faf889` で棄却)
- 採用理由: KV をリクエスト間で保持できれば 2 回目の prefill はほぼ 0 になる。まずそれで足りると判断した。
- 観測: 同じ会話の 2 回目は速いが、別の会話が来た瞬間に元に戻る。前のエントリを捨てるため、交互セッションでは効かない。
- 棄却: P2 でマルチエントリ LRU(最長共通接頭辞が最大のものを選び、トークン予算 32k で退避)へ。交互 2 セッションで `reuse 47/48` まで到達した。

### 条件を書かずに速度向上を報告する(`67280c9` とその記録で棄却)
- 採用していた形: 「prefill 88 秒 → 24 秒」「decode 1 秒/トークン → 0.1 秒」という数値だけを残す。
- 観測: モデル・プロンプト長・スレッド数の明記が無く、条件付きの比較として使えない。後から同じ条件を再現できない。
- 棄却: 交互 A/B・cold 単発・アンカー md5 を条件として必ず添える規律へ移行した。

### 出力の正しさを目視で判定する(初期実装の時点で棄却)
- 採用していた形: 実モデルを通して文章として読めるかどうかで正しさを判断する。
- 観測: 意味を成さない出力に対して、どこが違うのかを言えない。型検査も panic も起きないため、欠陥が表面化しない。
- 棄却: 合成モデルで決定論だけを見る層(`testutil.rs`)と、実モデルで基準文字列の一致を見る層(exactness)の 2 段構えへ。
