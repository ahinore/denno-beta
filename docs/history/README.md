## 全体像

denno は Rust で書いた LLM 推論エンジンで、CPU の参照実装と CUDA カーネルを**同じ数値経路**で持ち、
GPU に載せても出力が変わらないことを契約にしている（`docs/NUMERIC_POLICY.ja.md`）。
対象は Qwen3.5 系（Gated DeltaNet ハイブリッド）で、9B int8 と 27B q4 を同じバイナリで動かす。
API は Anthropic Messages 互換で、ローカルのデスクトップアプリから使う。

読むのに必要な前提は 3 つだけ。

- **prefill**（プロンプトを読む処理）と **decode**（1 トークンずつ生成する処理）は別物で、
  ボトルネックも違う。数値は必ずどちらの話かを意識して読む。
- **アンカー**は「同じ入力なら同じ出力になる」ことを確かめるための md5 の基準値。
  数値経路を変えたらアンカーが動く。動かしてよいかの判断がこの開発の中心にある。
- **cold / warm** の区別。同じプロンプトの 2 回目は prefix cache に当たるので、速度の話は
  必ず「cold の単発」か「同一セッション内の相対」かを確かめる。

## 数値の読み方

1. **分母を先に読む**。モデル（9B int8 / 27B q4）、トークン数、cold か warm か。
   分母が違う数字を並べて「何倍」と言わない。
2. **prefill は cold・nonce 付き・中央値**が正式値（`scripts/prefill_bench.py`）。
   同じプロンプトの 2 回目は prefix cache に当たるので比較に使えない。
   3,161 token と 12,850 token では別の数字として扱う。
3. **decode は ms/token**。ウォームアップ 1 回は捨てる。TTFT と生成速度を混ぜない。
4. **推定と実測を区別する**。この索引と各巻では、コンテナ内で測った値を「実測（コンテナ）」、
   GPU 側の見込みを「推定」と書く。推定を確定値として引用しない。
5. **`DENNO_PROFILE` / `DENNO_PF_DBG` の % を KPI として引用しない**。
   PROFILE は計測そのものが対象を変える（SAMPLE=1 で実測の 2.7〜4 倍に膨らむ）。
   PF_DBG の位相は **wall の分割**であってカーネル時間の分割ではない。
   比を見たいときは nsys の GPU 側時間を使う。
6. **bench の m=1 の絶対値は L2 相対**（同じバッファを繰り返し読む）。
   判定は相対変化と実機 KPI で行う。
7. **アンカーの md5** は「出力が変わっていない」ことの証拠。数値が良くなってもアンカーが
   説明なく動いたら失敗として扱う。動かす場合は `docs/NUMERIC_POLICY.ja.md` の手順で明示的に再基準化する。
