# 第7巻 品質の切り分け — 崩れた出力を条件まで落とす

対象期間: 2026-10-15 〜 2026-10-22。生成品質が壊れたときに「どの条件でだけ壊れるか」を実測で絞り、
既定の出力を変えずに直し、壊れ方を GPU 無しで回せる装置に固定するまでの記録。
API の受理形式・配線・停止条件の実装は第2巻 `10_api_features.md`、決定論・アンカー・数値緩和は
`70_infra.md` にある。この巻は実装の説明を複製せず、切り分けの実測と判断だけを扱う。
日付は commit の author date の日付をそのまま使う(タイムゾーンは commit に記録されたもの。
JST に換算すると日付が変わる commit があるため換算しない)。

## この巻の問い

- 「出力が崩れる」という報告から、再現する条件をどう絞るか。何を固定し、何を振れば 1 条件に落ちるか。
- 直し方を入れたとき、既定の出力を変えずに済ませるにはどうするか(opt-in・既定 None・ビット no-op)。
- 品質の判定を、GPU の無い機械でも回せる形にできるか。できない部分を「未計測」として残す境界はどこか。

## 前提知識

greedy 復号(temperature 0)では、logits のわずかな差が語の選択を変え、以後の文脈ごと分岐する。
したがって「品質」の報告は、まず復号条件(温度・サンプラ・罰則)とプロンプト条件(system 長・tools 本数)に
分解しないと再現しない。chat template の描画、byte-level BPE のトークン境界、logits 加工の適用順も前提になる。
この巻の変更は logits の後処理とテキスト後処理が中心で、forward の数値経路には触れていない。

## 読む順序

A2.5(repetition penalty の本体)→ s53c(brief の意味変更)→ s53/s53b(停止の誤爆)→ s56/s57(反復抑止の opt-in)→
s56b(9B + tools の崩壊切り分けと serve 既定)→ s98/s100(needle 想起)→ s103/s107(10 ターン会話)→
s162(長文脈を既定ゲートへ)。前半 3 本は「既定の意味を変えるかどうかの判断」、後半 5 本は
「壊れ方を装置に固定する」話である。s53c と s53/s53b は同じ週の話だが、前者は thinking、
後者はテキスト後処理で、触っている層が違う。

## A2.5: repetition penalty を opt-in で入れる (2026-10-15, `4fada3c`)

**意図**: Qwen3.5-9B が temperature 0 の greedy で同じフレーズを繰り返し、文が前へ進まない。
まず疑うべきは chat template の描画だが、それは別に検証し、**テンプレートは公式準拠で不一致なし**
(反復の原因ではないと確定)だった。残る手として、既出トークンへの罰則という標準手段を入れる。
ただし既定の出力は 1 バイトも変えない。

**つまずき**: 強さの当てが外れた。`penalty` 1.15 と 1.3 は抑制が過剰になった。
1.1 が適正で、これは llama.cpp の既定値と一致した。もう 1 つのつまずきは「入れた瞬間に既定が変わる」
ことである。`penalty == 1.0` をビット完全 no-op として実装し、露出はリクエストの任意フィールドと
CLI フラグに限った。サーバーの decode 2 経路(逐次とバッチ)のサンプル直前に同じ関数を通す形にした。

**発見した課題**: 9B int8 の 2 本の payload で、1.1 はループを破って思考構造を保った(出力 md5 は
2 回連続と再起動後で一致 = 決定論は維持)。しかしこれは**症状の抑制**であって、反復退化の数値的な原因の
説明ではない。同一 GGUF を llama.cpp で回した場合との比較が残った。また「既定を 1.1 にする」判断は
しなかった。既定を変えると全リクエストの出力が変わり、アンカーと CPU 参照 md5 の前提が崩れるためである。

**次の方針**: 既定は None(指定なし)のまま、運用で明示的に指定する形へ寄せる。品質の最終評価は
GPU 実機での人間対応として残す。この「opt-in で入れてから計測する」順序が、この後の反復抑止 3 種と
serve 既定フラグの型になった。

## s53c: brief を「思考無効 + 簡潔指示」へ変える (2026-10-18, `e7246b8`)

**意図**: thinking は off / brief / full の 3 モードで入れた。brief は既定で、当時は
「思考は ON のまま、system 冒頭に短答誘導文を注入する」ソフト制御だった。既定で思考が走るのは
品質事故の温床なので、既定の意味そのものを点検する。

**つまずき**: 誘導文では直らなかった。**4 候補の誘導文を試して、いずれも 9B は「Thinking Process:」の
メタ分析を延々と書き、回答に到達しなかった**。system を短くしても同じで、長い system のせいではない。
原因は制御の種類で、誘導文は生成を制約しない。思考が走り始めれば、文面の強さは結果に効かない。
4 候補の文面はリポジトリに残っていない。記録にあるのは、s53c の直前までコードにあった s47 の 1 本
(「思考は短く数文で済ませ、すぐに回答を書いてください。」)と、置き換え後の 1 本だけである。
残っているのは結果だけ: 4 候補とも回答に到達しなかった。
抜け方は、brief を off と同じく**思考を無効化**し、そのうえで簡潔指示を注入する形に変えることだった。
Anthropic マップの `enabled` も off 扱いに揃えた(受理形式そのものは第2巻)。

**発見した課題**: 既定の意味が変わるので、既定に依存している wire テストの基準側を同時に更新する必要が
あった(エンジン直実行系は system 無しのままなので影響なし)。副作用として「思考は明示的に full を
送らないと走らない」運用になった。これが後で「思考は切られているのに温度 1 だけが残る」問題と
組み合わさる(温度側の対処は第2巻の `--temperature-cap`)。

**次の方針**: 「誘導文で生成を制御できる」という前提を捨て、テンプレート変数のようなハード制御に寄せる。
品質の判断は、モデルに何を書かせたかではなく、**回答に到達したか**で見る。この巻の以降の phase は
すべてこの見方で書いてある。

## s53/s53b: ロールラベル停止の誤爆と修正 (2026-10-18 / 10-19, `b1f5655` / `f21a985`)

**意図**: 生成テキストに次の発話者ヘッダが現れると、モデルはそのまま別ロールの文章を書き始める(偽ターン)。
llama.cpp の reverse prompt に相当する停止をテキスト後処理で入れ、あわせて既定の生成長を 4096 から
1024 に下げる。数値経路には触れない。

**つまずき**: 誤爆した。**実測で 23 tok と 44 tok で切れた**(記録にモデル名と量子化は残っていない)。
本文が短いうちに止まるので、長い回答が出ない。原因は判定の基準で、停止判定を「まだ送出していない部分」に対して行っていた。チャンク境界が
単語の途中に落ちると、本文中の `system` / `user` が「行頭の単独ラベル」に見える。加えて、マーカーが
トークン境界をまたぐため、確定前に `u` / `us` / `use` が delta に漏れていた。
抜け方は 2 つで、(1) 判定を**テキスト全体 + 未送出境界**の 2 引数にし、行頭はテキスト全体の `\n` 基準で
求める、(2) 末尾がマーカーの prefix になり得る間は送出しない holdback を入れ、`sent_len`(送出済みバイト数)
を不変条件にする。修正後は **1,024 tok まで正常**(既定の生成長に到達するまで誤停止しない)。

**発見した課題**: 「送出済み境界を 1 つの整数で持つ」という不変条件が無いと、行頭判定は成立しない。
もう 1 つ、prefix 経路は語境界を見ないため、改行後の `userland` でも holdback の後に停止し得る。
これは安全側(止まりすぎる)なので受容し、限界として記録した。テストは 12 バイト境界・CRLF・全角コロン・
行頭以外の非停止まで固定した。git の author date では修正 `b1f5655` が 10-18、機能の取りまとめ
`f21a985` が 10-19 で、修正のほうが先に着地している。

**次の方針**: テキスト経路の判定関数は、必ず「全体」と「境界」の両方を引数に取る形へ統一する。
後の SSE アセンブラと切断検知も同じ発想(境界を 1 つの整数で持つ)で書かれている。

## s56/s57: 反復抑止を 3 種 opt-in で足す (2026-10-19, `b3eaf71`)

**意図**: repetition penalty 1 本では、長い文脈での反復崩れを抑えきれない。OpenAI 互換の
`frequency_penalty` / `presence_penalty` と、llama.cpp / HF 互換の `no_repeat_ngram_size` を
**追加の opt-in** として足す。既定にしない理由は単純で、4 種のいずれも logits を変えるからである。
既定を変えると全リクエストの出力が変わり、アンカーと CPU 参照 md5 の前提が崩れる。
既定はすべて無効で、出力は従来とビット完全一致にする。

**つまずき**: 4 種類の補正が同じ logits に順番に効くので、**適用順がビット契約になる**。
順序を「生 logits → repetition → frequency → presence → no_repeat_ngram(-inf)→ temperature → top-k →
top-p」に固定した。ここで正直な限界が出た。frequency と presence の**内部**順序は f32 で観測できる
(別々に減算すると丸めが変わる)のでテストで殺せる。一方 no_repeat_ngram を frequency/presence の
前後どちらに置いても f32 では観測できない(-inf マスクが前段の減算結果を上書きする)。変異テストでも
生存した。つまり「最後に置く」ことはテストでは固定できない。

**発見した課題**: 既定 no-op は、無効値(`1.0` / `0.0` / `-0.0` / `n<=1`)の全組み合わせで logits が
ビット不変であることをテストで固定する必要があった。`is_noop()` が真なら文脈構築も counts 確保も
省くので、既定経路のコストまで変わらない。残った課題は品質評価で、反復崩れが実際に抑えられるかは
GPU 実機なしでは判定できない(人間対応)。量子化との相互作用も未評価。

**次の方針**: 観測できない順序は、テストではなくコード構造と文書で担保する。この割り切りは
`docs/NUMERIC_POLICY.ja.md` の「測れないものを測ったことにしない」と同じ扱いである。既定は変えず、
opt-in を入れてから実機で測る順序を崩さない。

## s56b: 9B + tools 9 個の崩壊を条件まで落とす (2026-10-19, `a9dd857`)

**意図**: 実セッションで 9B の応答に**偽の `user` ターン**と **`.showError warning` の混入**が出た。
これを「モデルが悪い」で終わらせず、再現する条件を特定して、運用側で回避できる形にする。

**つまずき**: 最初の見立て(文脈が長いから崩れる)は外れた。条件を次のように分けた。

- 固定したもの: モデル(Qwen3.5-9B int8)、復号(temperature 0 = greedy)、プロンプト本文、シード。
- 振ったもの: system の長さ、tools の本数、tools スキーマの大きさ、`repetition_penalty` の有無。

結果は次の 1 行に集約される。**6,223 tok(system 約 2.6k + tools 9 個 約 3.6k)のときにだけ崩壊した**。
同じ 6k 級の文脈でも tools が無ければ正常、tools があってもスキーマを縮めれば正常だった。
つまり崩壊条件は「長さ」単独ではなく「長い system + tools 9 個」の組み合わせである。
`--repetition-penalty 1.05` を付けると同一プロンプトで正常な短答が返った。

**発見した課題**: 対策を既定にできない。既定を 1.05 にすると全リクエストのサンプリングが変わり、
アンカーと CPU 参照 md5 の前提が崩れる。そこで serve に既定値フラグを置き、**リクエストが
`repetition_penalty` を指定しなかったときだけ**適用する形にした。フラグを付けない起動は `None` のままで、
出力は従来とビット完全一致する。0 以下・非有限は起動時に拒否する。本番の起動スクリプトは 1.05 を明示する。
なお 1.05 は A2.5 で適正と判断した 1.1 より弱い値で、決めた文脈が違う(A2.5 は短い 2 本の payload、
ここは 6,223 tok の tools 文脈)。

**次の方針**: 崩壊の条件が「tools の本数」に依存する以上、tools を減らすかスキーマを縮めるのが
クライアント側の本来の修正になる。サーバー側は安全弁として残す。この切り分け手順
(固定するものを先に列挙し、1 つずつ振る)は、後の 27B の品質調査でも同じ順序で使われた。

## s98/s100: needle 想起を GPU 無しの回帰にする (2026-10-20, `a0afc03` / `7543158`)

**意図**: 「長文脈で崩れる」系の不具合には、これまで再現手順が無かった。長文脈の needle 想起は
一度だけの使い捨て試験(4,671 token)で終わっていた。これを 1 コマンドの台本にして、ビルドを替えるたびに
同じ判定が返るようにする。

**つまずき**: filler を固定しないと、毎回違う payload になり回帰を比較できない。fixture に固定した
LCG と 6 つの語表から filler を組み立て、同じ fixture からはバイト同一の payload が出ることを
子プロセス 2 本の実リクエスト本文の突き合わせで固定した。needle は filler と無関係な話題
(倉庫・事務の作業)の英文に置くので、答えが局所文脈から出ることはない。判定は語境界つきで、
`QX-44715` のような紛らわしい近傍は想起成功とみなさない(単純な部分一致なら通ってしまう)。
s100 で chars/token = 5.1785 の実測に合わせ、`filler_chars` を 21,400 から 24,000 へ一度だけ補正した。
payload は 24,113 chars、**約 4,656 token は推定**であって実測ではない。

**発見した課題**: 終了コードを 3 値に分ける必要があった。0 = 想起 OK / 1 = 想起失敗(回帰)/
2 = 通信・解釈の失敗。「測れなかった」を「壊れた」と誤報しないためで、2 を 1 に混ぜない。
トークン数はサーバが返す `usage` だけを採り、返らなければ「未計測」と書いて数字を作らない。
検出器そのものは偽サーバを立てた 25 tests で検証した(正常・誤答・近傍・省略・HTTP 500・未接続・
非 JSON・404 fallback・決定論・標準ライブラリのみ)。

**次の方針**: 実サーバに対する想起と実トークン数は人間対応として残す。チェッカーが証明できるのは
「検出器が決められた文字列で正しく発火する」ことと「偽サーバに対して正しく動く」ことまでで、
モデルの実際の挙動は未計測である。この境界の引き方は s103/s107 でも同じにした。

## s103/s107: 10 ターン会話を台本にする (2026-10-20, `65e4546` / `cef9384` / `1a063af`)

**意図**: 9B の会話が 2〜3 ターンで崩れるという報告はあったが、崩れ方を再現する台本が無かった。
固定の 10 ターンを流し、**返答を追記して会話を実際に伸ばす**(ターン N は 2N-1 メッセージ)形にする。

**つまずき**: s97 の試作には 2 つの欠陥があった。検出器が 4 種しかなく、温度上限の回帰を検出できなかった。
s107 では、s97 版を廃止する前に `--expect-cap`(受理温度が上限を超えたら失敗)を新しいチェッカーへ移植した。
もう 1 つのつまずきは温度の扱いで、こちらから既定で温度を送ると serve 側の上限の回帰を検出できなくなる。
そのため回帰検出は `--temperature 1.0 --expect-cap 0.7` の明示指定で行う。しきい値は両側から固定した
(23 文字は発火しない / 24 文字は発火する)。

**発見した課題**: 検出器は 7 種になった。`repeat_line`(24 文字以上の同一行が 3 回連続)、
`repeat_sentence`(末尾文の 3 回連続)、`long_line`(400 文字以上の返答で 1 行が 60% 以上)、
`template_marker`(行頭に単独の `user` / `assistant` / `<|im_start|>` 等)、`fake_turn`(空行の後の偽 `user`
ブロック)、`empty`、`max_tokens`。最後の 1 つは**報告のみで失敗にしない**(長い回答は崩壊ではない)。
終了コードは 0 = 崩壊なし / 2 = 崩壊 / 3 = 基盤の失敗。ポート 8080(serve 既定)と 8090(本番)は
接続前に拒否し、スクリプトはサーバの起動・停止をしない。s107 で全段を 1 コマンドにまとめた
(`scripts/run_cpu_checks.sh`: kernel invariants → engine lib → server → 各 self-test。最初の失敗で止まり、
全通過のときだけ 0)。

**次の方針**: 実モデルでの 10 ターン実行は人間対応。台本のしきい値は実機の応答分布を見てから調整する前提で、
初期値は偽サーバで検証した値である。台本は追記のみ可、並べ替え禁止とした。

## s162: 長文脈の回帰を既定ゲートに入れる (2026-10-22, `5931c7a`)

**意図**: 既定ゲートはすべて `DUMMY_CONTEXT = 64` で回っていた。本番が配信している 3,020 token の
prefill とマルチターン会話でしか現れない経路(KV キャッシュが初期容量を超えて成長する経路、
長い prompt での prefix cache の予算と退避、コンテキスト容量の境界)は、既定ゲートで一度も
実行されていなかった。

**つまずき**: 長文脈を回すにはテスト用のモデルが要る。`LongKvSensitiveModel::with_context(n)`
(context 4096・1 層・kv_dim 4・32 B/token)を足し、`forward` は既存の `KvSensitiveModel` に委譲して
KV 行の式と logits の組み立てを 64 token 版と同一コードに通した。既存テストとの重複も 1 本ずつ切り分けた
(64 token 以下でテキストとトークン数だけを見ていた、原始 API の assert を極小 `max_len` で見ていた、など)。

**発見した課題**: 追加 4 本はすべて既定ゲート(`#[ignore]` 無し)で、lib は 274 passed / 0.27〜0.29 s
(追加 4 本だけなら 0.01 s)。kv_dim 4 なので 4,096 token でも KV は 128 KB で、長さを縮める必要は無かった。
一方で lib 全体を 45 回反復したうち 8 回、`prof::tests` のテストが 1 本落ちた(大域カウンタ共有の flaky。
追加 4 本は 45 回中 0 回)。テストの隔離は別 phase(s163)で扱った。

**次の方針**: 実モデル(27B q4 / 9B int8)の長文脈、4,096 超のコンテキスト、GDN の長文脈 prefix cache は
未計測として残す。この巻の装置が証明できるのは「決められた条件で検出器が発火する」ことと
「既定ゲートで長文脈の経路が実際に通る」ことまでである。

## 棄却カタログ

当時は妥当に見えたが後で捨てた手。棄却の理由は、そのときに観測できた事実で書く。

### brief を誘導文だけで制御する(s47 → s53c `e7246b8` で棄却)
- 採用理由: thinking の意味を変えずに、system 冒頭の指示文だけで回答に導けると考えた。ハード制御ではないと明記していた。
- 観測: **4 候補の誘導文を試して、いずれも回答に到達しなかった**。9B は「Thinking Process:」のメタ分析を延々と書き、system を短くしても同じだった。
- 棄却: brief を「思考無効 + 簡潔指示」に変え、マップ `enabled` も off 扱いへ。誘導文は生成を制約しないので、思考が走れば効かない。

### 停止判定を「未送出部分」に対して行う(s53 → s53b `b1f5655` で棄却)
- 採用していた形: `text[sent_len..]` を渡し、その先頭をテキストの行頭として扱う。
- 観測: **23 tok / 44 tok で切れた**。チャンク境界が単語の途中に落ちると、本文中の `system` / `user` が行頭の単独ラベルに見える。修正後は 1,024 tok まで正常。
- 棄却: 判定を「テキスト全体 + 未送出境界」の 2 引数にし、行頭は全体の `\n` 基準で求める。prefix 経路が語境界を見ない点は安全側として残した。

### repetition penalty の既定を 1.05 / 1.1 にする(A2.5 `4fada3c` / s56b `a9dd857` で棄却)
- 採用しかけた形: 品質が直るのだから既定にしてしまえばよい。
- 観測: 既定を変えると全リクエストのサンプリングが変わり、アンカーと CPU 参照 md5 の前提が崩れる。6,223 tok の tools 文脈では 1.05 で崩壊が消えたが、それは特定の条件での話である。
- 棄却: 既定は `None`(指定なし)のまま。serve の起動フラグとリクエスト指定で明示的に入れる。フラグ無しの起動はビット不変。

### penalty 1.15 / 1.3 を採用する(A2.5 `4fada3c` で棄却)
- 採用理由: 反復が強いので、強めの罰則のほうが確実に見えた。
- 観測: 1.15 と 1.3 は抑制が過剰になった。1.1 が適正で、llama.cpp の既定値と一致した。
- 棄却: 1.1 を適正値として記録し、運用の 6,223 tok 文脈ではさらに弱い 1.05 を使う。

### 「6k 文脈の長さが崩壊の原因」という読み(s56b `a9dd857` で棄却)
- 採用しかけた形: 文脈長が閾値を超えると崩れる、という単純な読み。
- 観測: 同じ 6k 級の文脈でも tools 無しは正常、tools があってもスキーマを縮めれば正常。崩壊したのは **6,223 tok(system 約 2.6k + tools 9 個 約 3.6k)の組み合わせ**だけだった。
- 棄却: 対策を「長さを削る」から「tools の本数・スキーマを見る」に変えた。長さだけを見ていると再現条件を取り違える。

### no_repeat_ngram の適用位置をテストで固定する(s56/s57 `b3eaf71` で棄却)
- 採用しかけた形: 4 種の罰則の順序を、すべて変異テストで殺す。
- 観測: frequency と presence の内部順序は f32 で観測できるが、no_repeat_ngram は -inf マスクが前段の結果を上書きするため、前後どちらに置いても f32 では差が出ない。変異テストでも生存した。
- 棄却: 「最後に置く」ことはテストではなくコード構造と文書で担保する。測れない順序を測ったことにしない。

### needle の判定を単純な部分一致にする(s98 `a0afc03` で棄却)
- 採用しかけた形: 期待文字列が含まれていれば想起成功。
- 観測: `QX-44715` のような紛らわしい近傍文字列でも一致してしまい、想起していない出力を通す。
- 棄却: 語境界つきの判定にした。検出器は偽サーバの 25 tests で、近傍・誤答・省略をそれぞれ落とすことを固定した。

### 終了コード 2(測れなかった)を 1(壊れた)にまとめる(s98 / s103 で棄却)
- 採用しかけた形: 失敗はすべて非 0 なので 1 本にまとめる。
- 観測: 通信失敗や非 JSON を「回帰」として報告すると、直す必要のないビルドを壊れたと誤報する。
- 棄却: needle は 0 / 1 / 2、10 ターン会話は 0 / 2 / 3 に分けた。基盤の失敗と品質の回帰を混ぜない。

### 10 ターン会話チェッカーが温度を既定で送る(s103/s107 で棄却)
- 採用しかけた形: 実セッションに近づけるため、こちらから温度を明示して送る。
- 観測: serve 側の温度上限は起動設定なので、チェッカーが上書きすると上限の回帰を検出できなくなる。
- 棄却: 既定では温度を送らない。回帰検出は `--temperature 1.0 --expect-cap 0.7` の明示指定で行い、受理温度が上限を超えたら失敗にする。
