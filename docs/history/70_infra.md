**この開発では「数字を信じてよい条件」を何度も作り直している。** 何を測り、何を測ってはいけないのか。

読み方は 2 通り。

- これから同じエンジンで計測する人: §1（装置の全体像）→ §6（落とし穴の一覧）→ §7（判定手順）

## 2. 検証の柱: アンカーと wide 比較

### 2.1 アンカーとは

固定の入力・固定のシードで生成した結果の md5。**同じバイナリ・同じ入力なら必ず同じ md5**になる。
数値経路を触った変更は、この 3 本（1b / 2b / full）が一致しなければ採用しない。

- アンカーの基準値は `data/verify/anchors_baseline.txt`。**リポジトリには入れない**（環境依存のため）。
- アンカーが動いたときは「意図した変更か」を必ず説明する。説明できない動きは**失敗**として扱う。
- 過去に何度かアンカーが動いている。動いた理由は 3 種類しかない:
  1. 数値緩和クラス（R1〜R4）を意図的に採用した（例: attention の GPU バッチ化）
  2. プロンプト自体が変わった（例: 既定の thinking モードが brief に変わった）
  3. **未初期化領域の読みなど、説明できない動き**（例: 一度ドリフトが出て、次のビルドでは再現しなかった例がある。
     これは未解決のまま残している。再現したら必ず止めて調査する）

### 2.2 wide 比較

アンカーは 3 本だけなので、変化を検出できない入力がある。そこで **8 問 × 150 token の出力を
`wide` ファイルに落として `cmp` で完全一致を見る**運用を併用する。1 バイトでも違えば不一致。

- 速度改善の受け入れでは「アンカー 3/3 MATCH」と「wide 一致」を**両方**要求する。
- 出力トークン数が大きく変わった場合は、数値誤差ではなくロジック退行を疑う（`NUMERIC_POLICY` §5）。

### 2.3 決定論の確かめ方

同一プロセス内の 2 回では不十分。**プロセスを再起動して 2 回測る**（`ANCHOR_REBASE.sh` の check モード）。
過去に「1 回目のリクエストだけ違う値になる」バグ（KV ミラーの世代不一致、ステップ内の再確保が
in-flight のカーネルのバッファを解放する）が出ているので、**起動直後の 1 回目を含めて**測る。

## 3. 速度の測り方の変遷

### 3.1 第 1 期: 「同一サーバで 2 回目」を正式値にしていた（誤り）

長いあいだ、同じプロンプトを 2 回流して 2 回目を正式値としていた。これは**prefix cache に当たる**ため、
prefill の比較には使えない。±30% のばらつきの主因がこれだった。

- 実際に、あるビルドで「−9.7%」と記録した数字が、cold で測り直すと −5.7% だった例がある。
- ウォーム 2 回目は「同一セッション内の相対比較」にしか使えない。

### 3.2 第 2 期: cold 単発 + 交互 A/B（正式手順）

現在の正式手順:

- **prefill**: `scripts/prefill_bench.py <文字数> <回数>`。**引数は文字数**でトークン数ではない
  （例: `16000` ≈ 3,161 token、`65000` ≈ 12,850 token）。プロンプトに nonce を混ぜて
  prefix cache を必ず外し、複数回の中央値を採る。
- **ビルド間の比較**: サーバを停止 → 起動 → 1 リクエスト、を 2 つのビルドで**交互に** 3 ラウンド。
  同一バイナリ内のばらつきは 1.5 ms 程度なので、それ以下の差は「変化なし」と判定する。
- **decode**: ウォームアップ 1 回を捨てて、ms/token の中央値。TTFT と生成速度を混ぜない。
- **受入の下限**: prefill の改善は 0.3 s 以上（cold）。それ未満は不採用（測定誤差と区別できないため）。

### 3.3 「計測窓」の運用

GPU は 1 台しかないので、計測は**窓**として宣言して排他する。

- 計測を始める前に判断ログへ【宣言】を書き、目的・使うポート・所要時間・終了条件を明記する。
- 窓が開いている間、他の担当はビルド・GPU_VERIFY・bench・共有ツリーの前進を行わない。
- 終了時に【宣言解除】と結果（実測値と採否）を書く。**結果の採否は窓を開いた担当が決める**。
- 窓を閉じ忘れると、他の担当が「待ち」で止まる。実際に何度か起きているので、
  監視側は「宣言が文面上まだ有効か」を毎回確認する運用にしている。

## 4. 計測装置ごとの注意（実測で分かっていること）

### 4.1 `DENNO_PROFILE` の絶対値は使えない

計測自体が対象を変える。サンプリング無し（全 span）では実測の **2.7〜4 倍**に膨らむ
（例: 実測 33.5 ms/token のところ 137 ms/token）。サンプリング（N step に 1 回だけ span を取る）を
入れても 10% 前後のオーバーヘッドが残る。

→ **絶対値は使わない。比だけを見る。** 比を見るときも nsys の GPU 側時間で裏を取る。

### 4.2 プロファイル会計は何度も作り直している

「区間の合計が wall を説明しない」問題が繰り返し出た。対策として積み上げたもの:

- `via` 列（CPU 経路か GPU 経路か）を実測で出す
- `tok/call` の分母を直す（呼び出し回数とトークン数を取り違えない）
- 残余を「全体 − 段」で定義する（`sl_lin_other` / `sl_step_other`）
- 計測点そのものを分離する（`d2h_state` を logits / kv_flush / gdn_flush / attn_pf に割る）

**教訓**: 「その他」を放置すると、そこに本当のボトルネックが隠れる。残余には必ず名前を付ける。

### 4.3 `DENNO_PF_DBG` の位相 % は KPI ではない

位相バケットは **wall の完全な分割**であって、カーネル時間の分割ではない。
バケットには「その区間で発行したカーネル + GPU アイドル + ホストの遅れ」が混ざる。
したがって「ffn_down が 17.6%」は「ffn_down のカーネルが 17.6% の時間を使った」ではない。

- 位相の % を KPI 表に書かない。
- 分母（その run の wall）を必ず添える。分母が 6 倍違う run の % を現在値として引用しない。

### 4.4 ncu は使えない

カーネル内部（SM 占有率・命令種別）を見るには ncu が要るが、この環境では
`ERR_NVGPUCTRPERM` で拒否される。解除にはホスト側の設定変更とコンテナの作り直しが必要で、
その間サーバが止まる。**メンテ時間まで放置**と決めている。

代わりに使えるもの: `ptxas -v`（レジスタ・スタック・スピル）、`cuobjdump -sass`、
`nvdisasm`、`compute-sanitizer`、ホスト側 CUDA イベントによる区間計測。

### 4.5 nsys

カーネル別の GPU 実時間と H2D/D2H の回数・バイト数が出る。**相対比較に使う。絶対値は実機 KPI で取る。**
CUPTI の activity は権限不要で動く。

### 4.6 bench の m=1 は L2 相対

同じバッファを繰り返し読むので、L2 に載った状態を測っている。**帯域の上限を見るのには使えるが、
実機の速度の予測には使えない**。判定は相対変化 + 実機 KPI。

## 5. 数字を信じてよい条件（引用する前に確認する 6 項目）

1. **分母**: モデル（9B int8 / 27B q4）、量子化、トークン数、cold か warm か。
2. **cold か**: prefix cache に当たっていないこと（nonce 付きか、起動後 1 リクエストか）。
3. **中央値か単発か**: 何回測ったか。ウォームアップを捨てたか。
4. **実測か推定か**: コンテナ内で測った値（GPU なし）は「実測（コンテナ）」であり、
   GPU 側の値ではない。GPU 側は「推定」と書く。
5. **どの装置の数字か**: PROFILE / PF_DBG / nsys / 実機 wall。装置が違う数字を混ぜて「何倍」と言わない。
6. **アンカーは一致したか**: 数値経路を触った変更なら、速くなっていてもアンカーが説明なく動いていたら失敗。

## 6. 落とし穴の一覧（再発したものだけ）

### 6.1 ビルドとツリー

- 共有ツリーで複数のエージェントを同時に走らせない。ビルドは必ず別の `CARGO_TARGET_DIR` を使う。
- 共有ツリーの HEAD が古いまま作業を始めると、後で統合したときに手戻りする。
  **作業開始前に base が最新かを確認する。**
- `git add -A` を使わない。pathspec を明示する。過去に 43,249 ファイル（ビルド成果物と内部文書）を
  巻き込んだ事故があり、履歴の書き換えが必要になった。内部文書は `.gitignore` で除外している。
- 内部文書（作業報告・引継ぎ・検証スクリプト・検証データ）は commit しない。
  IP・ホスト名・ユーザー名が入るため。push 前の個人情報 grep は必須。

### 6.2 サーバの運用

- バイナリを差し替えるときは**先にサーバを止める**。動いているバイナリは上書きできない（Text file busy）。
- 停止に `pgrep -f` や `for p in /proc/*` + cmdline マッチを使うと、**実行中の自分のコマンドラインが
  パターンに当たって自滅する**（exit 143）。pid を先に取って明示的に kill する。
- ポートは 1 つを本番に固定する。同じ GPU に 2 インスタンス載せると VRAM が足りず、
  CPU フォールバックに落ちて「異常に遅い」状態になる（実測で 400 s 超）。
- 計測のためにサーバを差し替えたら、**必ず本番の引数で起動し直して health を確認する**。
  止めっぱなしが一番高くつく。

### 6.3 エージェント（開発側）の運用

- コンテナに日本語のプロンプトを渡すと `?` に化ける。プロンプトは ASCII で書く。
- ターン上限が来ると commit せずに止まる。**「上限に近づいたら commit する」を毎回伝える。**
- 起動は「スクリプトを送る → md5 を確認 → 起動 → プロセスを確認」の順。1 回の ssh で複数の標準入力を
  繋ぐと 2 つ目が空になる。
- バックグラウンド起動は即死しても分かりにくい。ログに終了コードを必ず落とす。

### 6.4 計測環境の汚染

- GPU に常駐プロセス（画面配信・別の python など）があると util が 38〜47% で張り付き、数字が汚れる。
  bench は util 0〜5% の窓で取る。
- 計測中に他のビルドや別の bench を走らせない（load average と available メモリを先に確認する）。
- 計測の直前に uptime と空きメモリを見る運用にしている。急に遅いときは、まずそれを疑う。

## 7. 判定手順（受け入れの順序）

前段で落ちたら次を測らない。順序を守るのは、数字の帰属を崩さないため。

1. **ビルド + CPU ゲート**: 対象の commit が HEAD にあり、未 commit の実装が混ざっていないことを確認してから
   `cargo build --release` と `cargo test --release --lib`。
2. **GPU_VERIFY**: アンカー 3/3 MATCH・`RESULT: PASS`・health ok。終了後に本番引数で起動されていることを確認。
3. **実機 decode**: ウォームアップを捨てて中央値。基準から悪化していないこと。
4. **実機 prefill**: cold・nonce・中央値。文字数の引数を守る（小さい引数で測ると基準と比較できない）。
5. **ビット一致**: wide 比較。
6. **採用**: 数値が変わったら旧 md5 → 新 md5 を必ず記録する。`.cu` を触った commit は
   PTX の再生成が必要（`nvcc -ptx -arch=compute_75 -fmad=false -O3`）。

**やってはいけないこと**:

- アンカーを測らずに commit する
- 検証を通すためにテストや許容値を緩める（テスト側の変更は別 commit で理由を書く）
- 未 commit のソースが混ざったツリーで受け入れ計測をする（数字が誰のものか分からなくなる）
- 速度・リファクタ目的でアンカーを再基準化する（再基準化は数値緩和を採用したときだけ）

## 8. この巻の棄却カタログ（運用・計測の側で捨てたもの）

- **同一プロンプトの 2 回目を prefill の正式値にする** — prefix cache に当たる。cold で測り直したら
  −9.7% が −5.7% だった。以後 cold 単発 + 交互 A/B を正式手順にした。
- **`DENNO_PROFILE` の絶対値で速度を語る** — 計測そのものが 2.7〜4 倍に膨らませる。比だけを使う。
- **`DENNO_PF_DBG` の位相 % を KPI 表に入れる** — wall の分割であってカーネル時間の分割ではない。
- **ncu でカーネル内部を見る** — 権限で拒否される。解除にはコンテナ作り直し（サーバ停止）が必要。
- **`pgrep -f` でサーバを止める** — 自分のコマンドラインに一致して自滅する（exit 143）。pid を先に取る。
- **`git add -A` でまとめて commit する** — 43,249 ファイルを巻き込み、履歴の書き換えが必要になった。
- **共有ツリーの古い base のまま新タスクを始める** — 統合時に手戻りする。開始前に base を確認する。
