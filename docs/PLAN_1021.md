## 3. 構造的な原因（レビューの結論）

- **9B int8 は C4 chain 経路**で動く。1 step = 1 回の同期、層ループは全部デバイス上に enqueue（`docs/DECODE_PATH.md`）
- **27B q4 は per-op ラッパー** `maybe_gpu_linear_q4_into`（`quant.rs:334`）を通る。ホストスライスを引数に取るので、**1 step に 392 回の D2H と同期**が入る
- PROFILE（計測込み・92 step）の内訳: step 131.8 ms = lin 24.2（うち **d2h 21.9**）+ gap_fwd 54.2 + final/sampler 0.8
- したがって効くのは「カーネルの高速化」ではなく「**経路の付け替え**」。B18（per-call D2H を関数内で消す）が 392 → 385 しか減らなかったのは、`gdn_scan()` や `full_attn_core()` がホストスライスを取る設計だから。関数の境界を変えないと消えない

## 4. 計画（優先順）

### P0-1 KPI の定義統一と再測定（半日）

- 固定プロトコル: serve 起動 → 1 リクエスト（temperature 0・max_tokens 200）→ TTFT と (wall - TTFT)/tokens を 3 回、中央値
- 27B q4 と 9B int8 の両方で取る。`64c1163` のバイナリでも取り、55.1 がコード差か測定差かを切り分ける
- 成果物: `docs/KPI.md` に手順と現在値を固定

### P0-2 B19 を仕上げる（CPU のみ・進行中）

- `DENNO_PROFILE_SAMPLE=N`（N step に 1 回だけ span）で計測オーバーヘッドを 10% 未満に
- `gap_fwd` を GDN / full attention / rmsnorm / rope / quantize に分解
- 現状の 52 ms/step の gap を再現する CPU フィクスチャを追加（GPU 無しで回帰できる）
- 受入: 262+ テスト緑、`DENNO_PROFILE` 未設定で no-op、サンプリング時の膨張が 10% 未満

### P0-3 27B q4 の decode を chain 経路へ載せ替える（本命・最大のレバー）

段階を切る。各段階でアンカー 3/3 と bench 非悪化を関門にする。

1. **q4 線形を chain に載せる**: デバイス常駐バッファ同士で `dno_gemv_q4_0c4` を叩く入口を作り、層ループからホストスライスを排除。目標: **D2H/step < 5**
2. **要素演算のデバイス融合**: residual add + rmsnorm、swiglu、q4 activation quantize をデバイスカーネルに（`.cu` 追加 → PTX 再生成が必要）
3. **GDN scan / full attention のデバイス入口**: ホストスライスを取らない入口を追加し、KV stage の D2H を廃止

- 受入（段階 1 完了時点）: GPU util 40% → 70% 以上、decode 72 → **50 ms/token 以下**、アンカー 3/3 MATCH、9B の 16.3 ms/token が不変
- 受入（段階 3 完了時点）: decode **35 ms/token 以下**
- 禁止: 精度を落とす変更、GDN の形状変更（B11 の再試行）、アンカーを動かす最適化

## 5. 役割と進め方

- **dev**: コード変更と CPU テストまで。GPU ビルド・実測・アンカー・push は不可
- **supervisor**: 5 分毎。ビルド・実測・関門判定・状態カード更新。push はしない
- **メイン（私）**: push、設計判断、`.cu`/PTX、アンカー窓、KPI の最終判定
- 各タスクは「根拠の実測・触る場所・予測値・やってはいけないこと」を HANDOFF に書き、commit メッセージに `PREDICTION:` を必須にする
- 2 回失敗で打ち切り、3 タスク連続で改善なしなら計測と整理に切り替える（既存規律）
